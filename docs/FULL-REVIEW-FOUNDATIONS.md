## Commandes reproductibles

`npm run dev`, `npm run start`, `npm run build`, `npm run typecheck`, `npm run lint`, `npm run db:generate` passent par Node, sans affectation shell Unix ni `timeout` GNU sous Windows. `npm run check` exécute TypeScript puis tous les tests, en arrêtant sur une erreur. Les CLI des dépendances verrouillées sont invoquées directement avec le même runtime Node ; arguments passés sans shell.

La construction contrôle d’abord les segments V1 par `scripts/build-semantic-shards.mjs --verify`, puis construit Vinext ; aucune étape suivante ne démarre après un échec. Chaque étape est bornée par `SITES_BUILD_TIMEOUT` (3 minutes par défaut), arrêt de l’arbre de processus, code 124 sur expiration. `SITES_BUILD_KILL_AFTER` vaut 10 secondes par défaut. Les codes enfant restent inchangés ; une erreur de lancement retourne 69. État Wrangler, Miniflare, cache npm et temporaires restent sous `.sites-runtime`. Le home utilisateur et les secrets applicatifs ne sont pas réaffectés.

La vérification V1 ne réécrit aucun asset. Elle contrôle l’empreinte de l’index canonique figé (`6f7135f02473c70f0b13fbd62709fc23a1b2ca45294b7c2cdaef29a2c691f137`), la copie publique, la source exacte et les 120 objets compressés, puis recalcule intégralement leurs scores/rangs/ordre depuis la source V1 pour comparer leurs payloads. La génération explicite historique `npm run semantic:shards` reste disponible pour une reconstruction contrôlée ; elle ne fait plus partie de la construction de production. Le header gzip porte un octet OS différent sous Windows (10) et Linux (3) : régénérer puis adopter les nouvelles empreintes serait une mutation de V1, même avec les mêmes scores. Les tests protègent les octets et le diff Git avant/après vérification et refusent un objet ou index altéré sans les remplacer.

`npm run install:ci` conserve sous Linux le helper officiel Sites existant : précontrôle du tarball verrouillé, cache semé éventuel, télémétrie et verrou `flock`. Sous Windows, le helper Node lance le runtime npm qui a invoqué le script (`npm_execpath`), `npm ci`, un guard exclusif portant le PID, et un délai de 8 minutes. Un guard abandonné nécessite de vérifier son propriétaire ; il n’est pas supprimé automatiquement. L’intégrité npm du lockfile est conservée. Aucun paquet n’a été changé et le lockfile ne nécessite donc pas de réécriture. Aucun script d’installation n’est requis pour construire si l’installation autorisée est déjà complète.

### Index SQLite de staging

La reconstruction et le vérificateur indépendant avaient un commit SQLite par mot, rendant le test de 50 001 lignes extrêmement lent sous Windows. Ils utilisent désormais des transactions d’au plus 4096 insertions, gardent `synchronous=FULL` et le verrou de génération. Le préfixe d’index validé reste disponible pour la déduplication ; le reste est annulé en sortie ou en erreur. Cet index est jetable : toute reprise le reconstruit depuis les segments et checkpoints contrôlés, qui restent les seules autorités durables. Un journal de cet index laissé par un arrêt forcé est retiré seulement sous le guard exclusif lors de sa reconstruction. Aucune configuration de corpus, empreinte, normalisation, identité, règle de score ou voie d’activation n’a changé. Le vérificateur conserve son implémentation indépendante.

Ruling supplémentaire D02 : `scripts/canonical-gzip.mjs` fixe l’octet OS du header gzip à 3, l’enveloppe Linux historique, avant empreinte et écriture immuable. Les générateurs locaux de corpus BRV2, d’index BPI2, de cible BRT2 et la génération V1 explicite réutilisent ce helper. Il ne modifie ni données décompressées, ni compression deflate, ni configuration ou pins historiques. Preuve sur un vrai objet V1 : 166 390 octets identiques à l’original après normalisation ; le seul delta du gzip Windows natif était l’octet 9 (10 au lieu de 3). Une fixture V2 réelle de test contrôle corpus, index et cible par leurs trois vérificateurs indépendants, plus recompression exacte des objets. Un staging Windows non canonique commencé avant cette correction est laissé intact ; le contrôleur reprend officiellement dans un nouveau staging, sans adopter ses empreintes ni supprimer son verrou. Une autre version de zlib peut encore nécessiter qualification contre les pins exacts : les références ne sont jamais réécrites pour masquer une différence.

## Diagnostic et mesure (D27)

`lib/product-events.ts` définit le journal local `braiz.diagnostics.v1`, version 1, 100 dernières actions et taille de lecture maximale de 32 Kio. Chaque entrée comporte seulement `type`, `context` (énumérations fermées) et `occurredAt` réel. Aucun mot, solution, score, référence de puzzle, identifiant d’appareil, pseudonyme, invitation ou contenu libre n’est accepté. Les schémas futurs, sensibles ou corrompus sont conservés et bloquent toute écriture plutôt que d’être remplacés. Les erreurs de stockage ne bloquent pas le jeu.

Les consommateurs appellent `recordProductEvent(storage, type, context)` après une action réellement acceptée. Ne pas appeler à la restauration, à la relecture, au rendu, ou pour reconstruire une activité historique. L’action volontaire d’import peut être observée comme `profileImported`, mais jamais les faits importés. Les réponses réseau et les refus de vocabulaire sont deux types distincts. Aucun appel externe ni cookie de mesure : `ProductDiagnostics` fournit téléchargement explicite et effacement volontaire. Il faudra le monter dans le profil du lot 2/3. À ce stade seuls les points de raccordement sont livrés : aucune activité de joueurs n’est affirmée observée.

Définitions de raccordement : `firstGuessAccepted` seulement lorsque le premier essai d’une partie vide vient réellement d’être accepté ; `guessAccepted` pour chaque proposition acceptée ; `guessRejected` pour un refus de lexique ; `networkFailed` pour une panne ; `gameLeft` seulement à une sortie volontaire effective du jeu (ne prouve pas un abandon définitif) ; `gameResumed` à une reprise choisie ; `shareCopied` seulement après copie réussie ; `refusedWordReported` seulement après action volontaire de signalement, sans le mot dans le diagnostic. Les autres types nomment une action précise (indice, victoire, aide, bilan, prochaine activité, export/import de profil, téléchargement/ouverture du pack). Fermeture de navigateur, abandon ultérieur et rétention ne sont pas déduits.

Ce journal ne prouve ni audience, utilisateurs uniques, adoption, attribution de retour, compréhension ou satisfaction. Les actions non raccordées restent non observées ; les actions effacées/au-delà du cap sont inconnues. Les onglets peuvent se remplacer mutuellement dans ce journal de support limité : ce n’est ni un compteur exhaustif ni une autorité de progression. Les résultats personnels et compétitifs restent dans leurs mécanismes existants.
